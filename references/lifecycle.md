# 需求演进与按需归档

仅在处理新需求、调整计划或归档历史时读取相关章节。沿用现有文档组织、任务编号和优先级约定，不为每个小需求增加全套流程。

## 需求演进

### 判断用户意图

| 意图 | 处理 |
| --- | --- |
| 讨论想法、以后可能做 | 在 TASKS 候选区或等价位置简记想法与来源，状态为候选；不表示已纳入范围，不自动开发 |
| 明确要求新增功能 | 用户要求本身是该功能的授权；检查相关影响，补充任务与可验证验收条件，不因最初未规划而拒绝或重问 |
| 替换旧功能、改变方向 | 依据用户明确要求标出范围、旧任务和决策的影响；未授权的关键取舍先澄清，只暂停依赖该取舍的部分 |

“整理这项需求”只授权整理；“实现这项功能”可以继续实现。候选被明确采纳时更新原任务，保留编号和来源，避免重复创建。涉及核心目标的明确调整可同步 PROJECT；不能由功能授权推断违反已有架构或数据兼容约束的技术手段也获批准。

### 检查影响并纳入计划

1. 只读取相关规划、接口/代码和决策，检查旧行为、模块依赖、数据格式/兼容、验证及回归范围。小需求做局部检查；不强制全项目审计。无法确定但不阻碍当前授权工作的细节写待确认。
2. 在任务中记录需求来源（日期、用户要求或既有文档位置）、目标、状态与验收标准；根据影响补充正常行为、关键边界和旧功能回归。AI 推导的验收细化应标明依据；影响用户预期的关键选择不得伪装成用户已确认。
3. 用户明确优先级时据此调整；未指定时保留当前任务，新需求进入后续计划。如果新要求本身明确要求现在实现，则作为本轮目标处理，不机械排到队尾；只在挤占其他已承诺交付、依赖或时间约束需要取舍时询问。
4. 按授权更新 PROJECT 中的范围，并在有实际架构变化时更新 ARCHITECTURE，注明依据；仅记录需求不表示实现完成。发现与有效约束冲突时分别保留需求授权、现有约束和待决技术方案。
5. 只有形成长期技术选择才更新 DECISIONS。新功能一般留在 PROJECT/TASKS；不为每个功能创建技术决策。

### 调整任务与恢复工作

- 候选：尚未采纳的想法；不能作为开发授权。
- 延期：保留目标、延期原因和恢复条件/重新评估时机，仍属活跃计划；不暗示取消。
- 取消：需有用户明确要求或既有授权依据，记录日期、原因及残留影响；不能由 AI 仅因优先级低而取消。
- 被替代：注明替代任务编号，替代任务指回旧编号；重大范围替换按已有授权处理。旧实现若已完成，不改写过去验收事实，记录“历史已完成，当前由 T-xxx 替代”；未完成的旧任务不勾选完成。
- 勾选仅表示有验收证据的完成；取消/被替代未完成任务保持未勾选并写状态，不能将其统计为完成。
- 延期、取消、替代和优先级变化均保留原因，不重编号。沿用已有优先级体系；无体系时用“当前 / 后续 / 候选”轻量分组即可，不强制重排原任务表。
- 恢复时结合依赖、风险和验证缺口提出具体下一步及理由，说明已有授权和待决事项。不得把建议自动变为实施授权，也不只被动等待用户重新描述整个项目。

## 按需归档

### 触发与资格

- 用户调用 `$project-memory archive` 时检查可归档内容；Sync 中已结束任务或重复状态明显妨碍找到当前工作时，可自动执行。文件数量、开发次数、时间经过或单纯存在完成项都不是强制归档理由。
- 只归档已完成、已取消、已被替代且不再影响当前工作的任务，以及已过时的 STATUS 记录。仍为当前依赖依据、存在未解决影响或需频繁查阅的记录可继续保留。
- 进行中、待开始、待确认、待验证、受阻、延期、候选以及任何仍有效的缺口/未决事项留在活跃文档。段落混有历史和未决信息时先分离，不能整段搬走隐藏问题。
- v0.2 不搬移 PROJECT、ARCHITECTURE、DECISIONS；不清理业务文件、测试证据、Git 历史或用户数据。归档不是删除历史，也不构成结束任务的依据。

### 保存、核对与精简

1. 检查 TASKS、STATUS 和相关引用，选择实际归档范围。沿用已有归档目录与命名；没有约定时在管理文档所在目录使用 `archive/YYYY-MM-DD-NN.md`，按本地日期和当日未用的递增序号命名，不覆盖已有文件。TASKS/STATUS 路径分散时优先 TASKS 所在目录，链接使用实际相对路径。没有适合内容就报告无需归档，不创建目录或空批次。
2. 先写入一份批次归档：记录归档日期、来源文件、任务原编号、原状态、目标、验收标准、验证证据、取消/替代原因及必要上下文。保留历史事实，明确是历史记录；不能压缩掉支撑结论的证据或补造缺失原因。
3. 检查从原文件移到归档后相对链接是否仍指向原证据；必要时调整相对路径，保留来源可追溯。核对拟移除内容已完整保存、任务编号唯一、证据引用可用，以及仍有效问题仍在活跃文档。已有证据缺失时标明缺口，保留相关原记录，不把归档当作验证通过。
4. 核对通过后才精简 TASKS/STATUS。TASKS 留历史索引（编号、标题、最终状态、归档链接），STATUS 保留当前阶段、必要的最近完成摘要、当前问题与下一步。已有编号锚点/标题或显式 ID 被引用时，在原位置保留相同锚点的简短转接条目；不能只留下无法跳转的总索引。
5. 发现无法核对、写入失败、潜在内容丢失或引用不能安全调整时，保留原内容，报告未完成的归档，不继续删除。归档已写入但精简中断时先对照已有批次恢复，不另存重复批次。无需再次询问常规文档整理权限；不借归档变更范围或技术决策。

### 重复执行与追溯

- 索引/转接条目不作为新历史再次归档；先查已有批次中的任务编号，重复调用无新增内容时不写文件或增加新批次。已有历史不悄悄改写，后续纠正添加有日期的更正并相互引用。
- 新任务编号在活跃任务和历史索引中查重，继续既有序列，不因完成项移出正文而重用。只有索引无法确定时才按需读相关归档，不默认加载全部历史。
- 日常恢复读活跃 TASKS、STATUS；查旧验收、取消原因、替代关系或审计差异时才跟随索引读取对应归档。
- 汇报自动或显式归档的范围、批次路径、保留的当前问题及核对结果。Audit 可以报告归档需要、引用断裂或未决事项被隐藏，但不得执行归档或修复。
